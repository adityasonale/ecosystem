llm-server

A personal LLM gateway built with FastAPI. Clients use the standard OpenAI chat-completions API and ask for a model by name. llm-server looks the name up in models.yaml, detects the model's format from its path, starts a backend plugin that suits the format and the machine, and forwards the request. It authenticates, routes, sets limits, records traces, and maps errors into the OpenAI error shape. It serves local models only, and never loads one itself: every model runs in a backend process, so the server has no torch or GPU dependencies.

Model loading: backend plugins

A model is a name and a path in the gitignored, per-machine models.yaml, with optional args, sampling defaults, a pinned backend, a port and a startup_timeout. The file is read again whenever it changes, so adding a model needs no restart. The first request for a model starts its backend. A request for a different model waits for in-flight requests to finish, then stops the old backend and starts the new one. The size check runs before the old model stops, so a model too big for the machine gets a 400 and the current one stays loaded.

There is no in-process fallback: a safetensors (hf) model on a machine with neither MLX nor vLLM, such as the Windows laptop, gets a 400. GGUF through llama-server is the path for the laptop; safetensors through vLLM is the path for a Linux GPU server.

A plugin is a backends.base.Backend subclass. It declares its formats and priority, says whether it can run on the detected hardware, and implements start, stop, chat_completion and open_stream. Extra plugins load from plugins: in models.yaml as module:Class.

Legacy prefix

llamacpp/<anything> (providers/openai_compatible.py) is still accepted. If <anything> is a name in models.yaml, it's the managed model. Otherwise it's forwarded untouched to a llama-server you started yourself at LLAMACPP_BASE_URL. Upstream 4xx errors pass through; 5xx or unreachable → 502; timeout → 504. The old in-process local/ prefix and POST /generate were removed in e12ea75.

Backpressure

One model is resident at a time. Requests for it run concurrently and the backend queues them (llama-server runs with one slot, -np 1).

  • A request for a different model waits up to DRAIN_TIMEOUT_SECONDS (120 s) for in-flight requests before the swap; if they don't finish, it gets 503 + Retry-After.
  • A model too big for the machine gets a 400, never a 503, because retrying can't help.
  • Karen's ChatOpenAI(max_retries=2) retries 503 responses with backoff. That's how the client and server sides of this fit together.

The model behind it today

Qwen3.5-9B-Q4_K_M.gguf, registered as qwen3.5-9b, on the Windows laptop's RTX 4060 (8 GB). It runs on Docker Desktop's bundled Vulkan llama-server with --device Vulkan1 -ngl 99 -c 8192 -np 1 --cache-reuse 256 --reasoning-budget 2048. It generates about 65 tok/s and processes prompts at about 670 tok/s. Karen switches thinking per role with chat_template_kwargs.enable_thinking (on only for research), because this build ignores reasoning_effort. Prompt caching works: Karen keeps the system message stable, and llama-server restores it from a context checkpoint, with its RAM prompt cache (--cache-ram, on by default) keeping each kind of call's prompt. About 274 of ~340 router tokens and ~516 of ~640 supervisor tokens come from the cache. --cache-reuse itself has no effect on Qwen3.5's hybrid layers.
