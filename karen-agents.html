Karen: tools and agents

Karen's abilities are tools, described once in the tool registry. One agent loop binds all of them (see the graph). Only four agent classes are left: the loop itself, two that the loop calls as tools, and the node that saves each turn.

The tool registry

core/tools.py describes every tool Karen can call once, as a ToolSpec: the tool, its group, its risk, its source (local or the MCP server) and four labels. It's built once as container.tools.

An unknown relationship or a missing speaker counts as a guest. Today every interface passes no speaker, which means the owner, so only "high asks first" has an effect. The other rows start working once speakers are identified (voice recognition, per-user IDs), and they're enforced in code before the tool runs, not by the prompt. The loop's research and check_connection tools aren't in the registry, so the gate runs them for anyone.

Other labels

LabelMeaningTools today
untrusted_outputThe result is outside content, treated as data. When one runs, the turn is marked untrusted and a later approval carries a warningsearch_tool, run_command, search_documents (and the loop's research tool)
asks_userThe call is a question for you, answered through an interruptask_user
read_onlyThe call changes nothing (no write, send, play or reconnect). Not the same as low risk: list_reminder is medium and read-only, veronica__play is medium and isn't. Nothing reads it yet; it will decide which calls must wait for an earlier resultcurrent_time, current_date, battery_status, list_reminder, search_tool, search_documents, veronica__ping, read_emails, search_track, now_playing. run_command is read_only only: an allowlist that writes nothing (GIT_OPTIONAL_LOCKS=0 stops git status refreshing the index), but recursive grep, du and find are heavy, so it runs alone
parallel_safeThe call may run on a thread at the same time as other calls of one reply. Kept separate from read_only because a read-only tool can still be unsafe to run concurrently (a shell, a shared connection). Nothing reads it yet. Both labels are off by default, so an unlabelled tool, and the loop's research and check_connection, run alone
  • Local tools are declared in tools/catalog.py, except search_documents: it needs the retriever, so AppContainer builds it and adds it with ToolRegistry.register. MCP tools are read live on every call, so a reconnect shows up at once, and get their group, risk and labels from config.yaml: tool_policy. An MCP tool with no entry goes in its server's group (veronica) at risk high, and the loop doesn't bind it.
  • Every local tool must declare a risk. A misspelt key or an unknown risk level in tool_policy fails startup, so a typo can't silently drop an approval.
  • The group field is for picking tools per turn later, once there are too many to send them all.

The terminal tool: restricted in code

run_command(command, arguments, cwd) in tools/terminal_tools.py is an allowlist, not a shell. The loop's prompt explains the limits so the model doesn't keep hitting them, but the limits themselves are enforced by the tool.

RestrictionHow
No shellsubprocess.run([...], shell=False): pipes, ;, &&, redirects, $() and globs don't exist
Allowlistdf, uptime, ps, ports (lsof), du, ls, find, head, wc, grep, and git status|log|diff|show|branch. Each command checks its own arguments: find allows only -name, -iname, -type and -maxdepth (no -exec or -delete); git takes no -c, no --output, no rev:path, and branch takes no names
PathsResolved with symlinks followed, and they must be inside terminal.roots (~/projects). Anything matching terminal.deny is refused: .env*, keys, config.local.yaml, .ssh, .git/config and similar. Recursive grep excludes the same names
Git hardening--no-pager, core.fsmonitor=false, an empty diff.external, --no-ext-diff and --no-textconv, so a repository's config can't run a program
Limits10 s timeout, 4,000-character output cap, a minimal environment
WhoMedium risk: it runs for the owner and family; guests are refused by the gate
InjectionThe tool is labelled untrusted_output, so a later approval in the same turn (an email) carries the warning

Anything that changes state (running tests, starting services) would be a separate high-risk tool, which you approve before it runs. It isn't built.

Adding an ability

  1. Write the tool: a LangChain @tool in tools/. Its docstring and return values are what the model reads; raise ToolException on failure.
  2. Add one ToolSpec to tools/catalog.py with a group and an honest risk: anything that sends, pays, posts or deletes for good is high. Add read_only=True only if it changes nothing, and parallel_safe=True only if it can run at the same time as other calls. For an MCP tool, add a tool_policy line instead. A tool that needs a startup service is built in core/container.py and added with ToolRegistry.register.
  3. The loop binds it on the next turn and the gate applies its risk. Nothing else needs registering.
  4. Add a rule to karenLoopRules only if the model misuses it, and a line to INTERNAL_CAPABILITIES (core/capabilities.py) if it's a new kind of ability. Run the benchmark after any prompt change.

A separate agent only when it earns it: its own multi-step workflow, or keeping untrusted content out of the loop's context, as research does. Expose it to the loop as one tool.
