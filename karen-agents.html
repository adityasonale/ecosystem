Karen: agents

Karen has eleven agents. Four are orchestration agents, fixed nodes in the main graph that every turn passes through. Seven are action agents, plug-ins listed in orchestrator/agents/registry.py that the supervisor can choose.

Every agent takes its tools from the tool registry by group (below), instead of filtering tool names itself. Every ReAct agent passes each tool call through the same gate, which checks the tool's risk against who is speaking (see the graph page). The ReAct agents call create_chat_model() with the default agent role, so the model's normal thinking stays on for tool use. Email and music bind their MCP tools when they're built, and again on first use if Veronica was down at startup.

The tool registry

core/tools.py describes every tool Karen can call once, as a ToolSpec: the tool, its group, its risk, its source (local or the MCP server) and two labels. It's built once as container.tools.

  • Local tools are declared in tools/catalog.py. MCP tools are read live on every call, so a reconnect shows up at once, and get their group, risk and labels from config.yaml: tool_policy. An MCP tool with no entry goes in its server's group (veronica) at risk high, so no agent binds it, and anything that later sees it must ask first.
  • Every local tool must declare a risk. A misspelt key or an unknown risk level in tool_policy fails startup, so a typo can't silently drop an approval.
  • This is the groundwork for the single agent loop (agreed, not built): the loop will read every tool and its labels from here, and its policy step will be the same gate. The group field is for picking tools per turn later, once there are too many to send them all.

The contract: ActionAgent

Defined in orchestrator/agents/base.py. Anything that fills it in and is listed in ACTION_AGENTS is fully wired in.

class ActionAgent:
    name: str = ""              # route value + node name "<name>_graph"
    description: str = ""       # what the supervisor sees when planning

The terminal agent: restricted in code

run_command(command, arguments, cwd) in tools/terminal_tools.py is an allowlist, not a shell. The prompt explains the limits so the model doesn't keep hitting them, but the limits themselves are enforced by the tool.

RestrictionHow
No shellsubprocess.run([...], shell=False): pipes, ;, &&, redirects, $() and globs don't exist
Allowlistdf, uptime, ps, ports (lsof), du, ls, find, head, wc, grep, and git status|log|diff|show|branch. Each command checks its own arguments: find allows only -name, -iname, -type and -maxdepth (no -exec or -delete); git takes no -c, no --output, no rev:path, and branch takes no names
PathsResolved with symlinks followed, and they must be inside terminal.roots (~/projects). Anything matching terminal.deny is refused: .env*, keys, config.local.yaml, .ssh, .git/config and similar. Recursive grep excludes the same names
Git hardening--no-pager, core.fsmonitor=false, an empty diff.external, --no-ext-diff and --no-textconv, so a repository's config can't run a program
Limits10 s timeout, 4,000-character output cap, a minimal environment
WhoMedium risk: it runs for the owner and family; guests are refused by the gate
InjectionOutput is wrapped as untrusted, and the agent is untrusted_output, so later plan steps (email) carry the warning

Anything that changes state (running tests, starting services) would be a separate high-risk tool, which you approve before it runs. It isn't built.

Adding an agent

  1. Create orchestrator/agents/<name>.py. Subclass AgentBase for a ReAct tool loop (set tool_group; the gate comes with it), or ActionAgent for anything else.
  2. Set name and description. Set capability if the user should hear about it, and untrusted_output if its output contains outside content.
  3. Implement from_container (usually cls(llm=create_chat_model(), tool_registry=container.tools)) and build (usually self.build_react_graph(checkpointer)).
  4. Add the class to ACTION_AGENTS. Nothing else needs editing. A duplicate route name raises an error at startup.

Check first whether a tool is enough. A new tool in an existing group is picked up by that group's agent with no code change: a ToolSpec in tools/catalog.py for a local tool, or a tool_policy line for an MCP tool. Give it an honest risk: anything that sends, pays, posts or deletes for good is high.
