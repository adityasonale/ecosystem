The boundaries are what define the architecture. Here is every boundary, with the shape of the data that crosses it. Change the code behind a boundary freely; change the boundary itself carefully.

① Interface → assistant

VirtualAssistant.run(query: str, thread_id: str = "session-001", speaker_id: str | None = None) -> {
    "pending":  bool,        # True = paused on an interrupt, waiting for an answer
    "question": str | None,  # what to ask the user when pending
    "response": str,
    "route":    str,         # "conversation" | "complete" | ...
}

speaker_id is who is talking. With no ID it's the owner, and an unknown ID becomes a guest. It's resolved by core/identity.py into state["speaker"] and added to the persona's and every action agent's system prompt. Interfaces identify the speaker: today none do, so it's always the owner. Later that will come from voice recognition or a Discord user ID.

Interfaces never see LangGraph types. To answer a pending question, call run() again on the same thread_id, and the assistant resumes instead of starting a new turn.

④ Karen → llm-server

POST http://localhost:8100/v1/chat/completions
Authorization: Bearer <LLM_SERVER_API_KEY>

{
  "model": "llamacpp/bonsai-27b",      // a models.yaml name; "llamacpp/" is an accepted alias
  "messages": [{"role": "system", ...}, {"role": "user", ...}],
  "temperature": 0,
  "reasoning_effort": "none",          // per role, from config.yaml
  "tools": [...]                       // ReAct agents only
}

Errors come back as {"error": {"message", "type", "code"}}: 400 bad request (unknown model, unsupported format, can't run on this machine, too big), 401 bad key, 502/504 upstream problems, 503 busy (with Retry-After). Karen's only client is llm/client.py::create_chat_model(role).

⑤ llm-server → backend

The same OpenAI body, with the model entry's sampling defaults filled in where the request left them out, and model set to what the backend expects. It goes to the backend process llm-server started for that model on 127.0.0.1 (a free port unless models.yaml pins one). Streaming is passed through as SSE bytes. A llamacpp/<name> that isn't in models.yaml still goes to LLAMACPP_BASE_URL.

⑥ Karen → Veronica (MCP)

SSE  http://localhost:8200/mcp/sse      Authorization: Bearer <VERONICA_API_KEY>
list_tools → [{name, description, inputSchema}]   → LangChain StructuredTool "veronica__<name>"
call_tool(name, arguments)                        → tool result (JSON)

MCPClient keeps one persistent event loop on a background thread, because an MCP session must stay on the loop that opened it. Synchronous code calls into it with *_sync methods.

The adapter (mcp_tool_adapter.py) turns each inputSchema into a typed argument model: string, integer, number, boolean, array and object keep their types and the server's defaults, so the model sees max_results: integer = 10. Optional arguments the model leaves out aren't sent, so Veronica applies its own default. Karen then gives each tool a group and a risk level (low, medium, high) from config.yaml: tool_policy; a tool with no entry is high. Veronica doesn't send them yet. MCP tool annotations could carry them later: readOnlyHint → low, destructiveHint → high, openWorldHint → at least medium.

⑨ Veronica's REST API

POST :8200/send-email   Authorization: Bearer <client key>
  {"to", "subject", "body", "cc"?}  →  200 {"status": "success", "message", "id"}
                                     403 recipient not allowed · 502 send failed · 503 not configured

For notifications to the owner. It has the same key check as MCP and no approval step, so to and cc must be in VERONICA_NOTIFY_RECIPIENTS. Email to anyone else goes through the MCP tool and Karen's approval step.
