Karen: memory & retrieval

There are two separate stores of knowledge: memory (what has happened with you, and what you've told Karen about yourself and your world), kept as plain records in SQLite, and documents (files you gave Karen), searched in the Qdrant server. Facts have a Qdrant collection too (karen_facts), as an index next to their SQLite records. Everything uses the same embedding model (MiniLM): documents and facts are searched in Qdrant, episodes are compared in Python.

The package

All of memory lives in memory/, behind one object. Callers use four methods and never see the deque, the turn log's tables or how episodes and facts are built.

What Memory depends on (passed in by AppContainer): an executor (the ThreadWorker) for background writes, the window size (config.yaml: short_term_memory.short_term_mem_context_size, 10), the embedding function and the recall counts (config.yaml: episodes and facts), and optionally a TurnLog, an EpisodeLog and a FactLog. A step's outcome is never parsed from text. Each tool call's status comes from its ToolMessage: error when the tool raised ToolException (an MCP tool does when its result is flagged isError, which Veronica sets for every {"error"} it returns), refused or declined from the approval gate, otherwise ok. A step that made no tool call (the agent only replied, e.g. "I can't see the draft") is no_action; one with an error or refusal is failed, one the user declined is cancelled, anything else success.

Episodes

An episode is one thing you wanted and everything around it, across as many turns as it took: the email that failed on auth, "try again", sent. It's stored as Observation → Action → Outcome. The LLM only groups turns and writes those three texts plus tags, people and importance. Everything the log already knows is filled in from the log: the status (the outcome of the last turn that acted, so a retried failure that worked is a success; no_action steps don't count as acting), the agents and tools, the times and the speaker (Karen's own turns, like a fired reminder, have none and are ignored). Turns the LLM leaves out stay unprocessed and come back next run, and an episode can name an earlier one it continues.

  • Cut at a pause. A batch ends at its last pause of at least episodes.gap_minutes (5): the gap to the next turn, or to now for the newest one. A back-and-forth still going on waits; once it goes quiet, it is built whole. A run of 30 turns with no pause is taken as is and its event carries on in the next batch, linked through continues, so building is never blocked for long.
  • One LLM call per run. Each run handles one batch; a backlog drains at 30 turns per run.
  • Its own worker. build_episodes is routed to the memory queue, served only by memory-worker. The reminder worker runs one task at a time, and a hung LLM call (300 s timeout, 2 retries) would hold every due reminder behind it.
  • Beat runs once. On Windows it is its own celery-beat process, because -B isn't supported there; in Docker it runs inside memory-worker (-B).
  • No duplicates. Before saving, a run claims its turns (processed = false → true); if another run (the script) took any of them meanwhile, it saves nothing.

The build call shares the GPU with live conversation, whichever process sends it. The pause rule and one batch per run keep that to one short call every 15 minutes at most.

Why it changed (2026-11-11): the old Qdrant episodic and semantic stores embedded raw chat, wrong answers included, and pulled "facts" out of events with an extra LLM call per turn. Recall then surfaced old mistakes as truth. They and the fact extraction are gone: memory is now a structured log of what Karen actually did, with statuses taken from the tools.

Why the pause rule (2026-11-13): the first background version took only turns at least 15 minutes old. That cut wherever the cutoff happened to land: one email exchange (draft declined, draft lost, sent to "your owner", sent) became three episodes, two marked success although nothing was sent. Waiting for Karen to go idle was ruled out, since an assistant is rarely idle for long; cutting at a pause in the past needs no idle time. The same exchange also showed two false successes in the log, fixed by no_action and by Veronica flagging its errors.

Facts (semantic memory)

A fact is something true about you or your world that stays true for a while: who people are to you, where things are, what you own, use or work on ("The user's sister is Priya.", "Priya lives in Mumbai."). Episodes keep what happened; facts keep what is so. They come from a second pass over the same turn log, with its own read flag, so the two builders never wait on each other.

Two stores, one truth. The SQLite facts table is the record: text, history, source turns, written in the same transaction that claims the turns. The Qdrant collection karen_facts is the index: one vector per current fact, point id = fact id, payload the speaker. The index is derived, so it can never win an argument: every extractor run starts by bringing it in line with the table (adds missing current facts, removes anything else). A Qdrant write that fails after the commit, or a wiped Qdrant volume, heals on the next run.

  • Only your words are a source. The LLM sees what you said and Karen's reply (for context: "yes, that one"), never tool results, so an email or a web page saying something doesn't become a fact about you. Requests, one-off events (those are episodes), Karen's own claims, questions about memory, preferences and small talk are ruled out in the prompt.
  • Changes, not a list. The LLM sees the known facts related to what you said (for each message, the 5 closest in Qdrant at 0.3 or more) and returns only changes. An update or delete must name a known fact; an update of an unknown id becomes an add, a delete of one is dropped, and a fact is changed at most once per batch. Every change must cite turns of the batch, or it's dropped.
  • Nothing is erased. An update or delete sets the old row's superseded_at to when you said it, and the new row's replaces_id points back. The old fact's vector leaves the index, so recall finds only current facts; scripts.py facts shows the history.
  • The worker embeds on the CPU. The memory worker loads its own MiniLM with device="cpu" (about 3 ms a fact), so it never takes GPU memory from the LLM, which is what kept episode embedding out of the worker (decision 35).
  • Filled in by code: when it was said (the latest cited turn), the speaker, the source turns. The LLM writes only the sentence.
  • Every turn read is claimed (facts_processed = false → true), including ones that gave no fact and Karen's own turns, which are never shown to the LLM. A clash with another run saves nothing, as for episodes.

Why it was rebuilt this way (2026-11-20): the old semantic store ran an extra LLM call on every turn, appended whatever it found (events and duplicates included) and recalled raw text. The rebuild reads settled batches off the turn log in the background, so the reply never waits; it only takes your words; and the model edits a known list instead of appending to it. Qdrant from the start, not vectors in SQLite: at a few hundred facts both are fast, but the related-facts search the extractor needs is a Qdrant query, and growth needs no rework.

Document retrieval (RAG)

  1. Ingestion (startup): DocumentLoader scans data/documents/<collection>/, optionally syncing from a GCS bucket first. It splits files and indexes only the ones not indexed yet into the Qdrant server (:6333), one collection per subfolder. A new server re-indexes everything once.
  2. Search: HybridRetriever.search(query) runs the vector search across all collections (top 20 candidates) and BM25 over the same documents.
  3. Fusion: weighted Reciprocal Rank Fusion merges the two rankings (BM25 0.4, semantic 0.6).
  4. Rerank: a cross-encoder (ms-marco-MiniLM-L-6-v2) keeps the best 5.
  5. Gate: documents go into the prompt only if the best cosine score reaches similarity_threshold (0.3). They're wrapped as untrusted documents data.
  6. Who calls it: the loop searches only when the model calls the search_documents tool (tools/document_tools.py), which runs the same search and gate and returns "No relevant documents found." below it. It is medium risk (guests are refused) with untrusted output.

The facts come first, one per line with the date they were said: [2026-11-20] Priya lives in Mumbai. Each event is one line: its time span, status, what you wanted, what Karen did and the outcome, e.g. [2026-11-13 10:41 to 10:44] (success) The user requested … What you did: … Outcome: The email was sent …. Each pending action is one line too: when, which agent (loop, or an old agent name on earlier turns), the task, the outcome, the reason if it failed and the tools used.

Which episodes are recalled

  1. The 3 latest, always. "What was the last thing I asked you to do?" and "and then?" point at the newest events by time, and their wording matches nothing, so similarity can't find them. They also carry what Karen was doing across a restart or another interface, which short-term memory doesn't.
  2. Up to 3 older ones by similarity. The message and each older episode (observation + action + outcome) are embedded with MiniLM and compared by cosine; those at 0.3 or more join, so "did my email to Aditya go?" finds it days later.
  3. Merged in time order, each episode once.

This runs on every turn, inside recall(). An episode is embedded the first time it's a candidate and stored in episodes.embedding, so only the message is embedded after that. The memory worker doesn't embed: it would load a second copy of the model on the GPU.

Which facts are recalled

Up to 5 current facts with a MiniLM cosine of 0.3 or more to the message: Karen embeds the message, queries karen_facts, and reads those ids from SQLite (current ones only), shown in the order they were said. There's no "latest" rule as for episodes: a fact matters only when the message is about it. Facts carry the speaker in the payload, but recall doesn't filter by it yet.

Scope to know about: short-term memory is one deque per process, not per thread_id. That's fine with you as the only user, but it's what would need changing if Karen ever served several people or parallel sessions. The turn log already records the speaker and thread of every turn.
