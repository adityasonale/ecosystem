Karen: memory & retrieval

There are two separate stores of knowledge: memory (what has happened with you) and documents (files you gave Karen). Memory lives in SQLite (data/karen.db); documents live in Qdrant.

The package

All of it lives in memory/, behind one object. Agents call five methods and never see the deque, the tables or how episodes are built.

What Memory depends on (passed in by AppContainer): an executor (the ThreadWorker) for background writes and the short-term window size. The TurnLog and EpisodeBuilder take a session factory and, for the builder, the LLM call, so both can be tested on a throwaway database with a stubbed model.

The turn-log write never blocks the reply. A conversation turn is logged with no steps; the steps left in the checkpointed state by an earlier action turn are ignored.

Turns and episodes

A turn is one exchange as it happened. An episode is one event: one thing you wanted and everything that happened around it, across as many turns as it took. "Send the report to Rahul" → the login fails → "why?" → "try again" → sent is three turns and one episode. The format follows the Observation → Action → Outcome pattern from this article.

Episode fieldFilled byHolds
observationLLMWhat the user wanted and the situation
actionLLMWhat Karen did, in order, errors, refusals and retries included
outcomeLLMHow it ended, one sentence
tags, importance_score, context.peopleLLMUp to 5 keywords; 0.2 lookup, 0.5 normal task, 0.8 personal or sent/paid/deleted/scheduled
parent_episode_idLLM, checkedAn earlier episode this continues (a retry hours later); must be one of the 5 it was shown
statusCodeThe outcome of the last turn that ran an action: success, failed, cancelled, partial (its steps disagree) or no_action
context.agents, context.toolsCodeFrom the steps' rows
started_at, ended_at, speaker_idCodeFrom the turns

Each turn records processed and episode_id. The builder reads the oldest unprocessed turns (30 per LLM call), and after checking the JSON it saves the episodes and marks their turns. Turns the LLM puts in skip (greetings, thanks, questions about Karen) are marked with no episode; turns it leaves out stay unprocessed and come back next run. python scripts.py build-episodes --dry-run shows one batch without saving.

Not built yet: running the builder automatically (waiting for an idle gap was ruled out), recall from episodes with the article's scoring (similarity, recency, importance), and compressing old episodes.

Document retrieval (RAG)

  1. Ingestion (startup): DocumentLoader scans data/documents/<collection>/, optionally syncing from a GCS bucket first. It splits files and indexes only the ones not indexed yet, with one Qdrant collection per subfolder.
  2. Search: HybridRetriever.search(query) runs the vector search across all collections (top 20 candidates) and BM25 over the same documents.
  3. Fusion: weighted Reciprocal Rank Fusion merges the two rankings (BM25 0.4, semantic 0.6).
  4. Rerank: a cross-encoder (ms-marco-MiniLM-L-6-v2) keeps the best 5.
  5. Gate: documents go into the prompt only if the best cosine score reaches similarity_threshold (0.3). They're wrapped as untrusted documents data.
