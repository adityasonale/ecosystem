Karen: memory & retrieval

There are two separate stores of knowledge: memory (what has happened with you) and documents (files you gave Karen). Both use one Qdrant client and one embedding model.

The package

All of it lives in memory/, behind one object. Agents call four methods and never see the deque, Qdrant, the record layout or the extraction prompt.

What Memory depends on (passed in by AppContainer): an embed function shared with document search, a Qdrant client, an executor (the ThreadWorker) for background writes, a FactExtractor, and the config values. memory/ reads no settings itself, which is what makes it testable with fakes and easy to move out as a service later.

Long-term writes never block the reply. Conversation turns under 4 words ("hi", "thanks") skip long-term storage; short action commands are still stored.

Document retrieval (RAG)

  1. Ingestion (startup): DocumentLoader scans data/documents/<collection>/, optionally syncing from a GCS bucket first. It splits files and indexes only the ones not indexed yet, with one Qdrant collection per subfolder.
  2. Search: HybridRetriever.search(query) runs the vector search across all collections (top 20 candidates) and BM25 over the same documents.
  3. Fusion: weighted Reciprocal Rank Fusion merges the two rankings (BM25 0.4, semantic 0.6).
  4. Rerank: a cross-encoder (ms-marco-MiniLM-L-6-v2) keeps the best 5.
  5. Gate: documents go into the prompt only if the best cosine score reaches similarity_threshold (0.3). They're wrapped as untrusted documents data.

Scope to know about: short-term memory is one deque per process, not per thread_id. That's fine with you as the only user, but it's what would need changing if Karen ever served several people or parallel sessions.
