Karen: memory & retrieval

There are two separate stores of knowledge: memory (what has happened with you), kept as plain records in SQLite, and documents (files you gave Karen), searched in the Qdrant server. Memory uses no embeddings; documents do.

The package

All of memory lives in memory/, behind one object. Agents call five methods and never see the deque, the turn log's tables or how episodes are built.

What Memory depends on (passed in by AppContainer): an executor (the ThreadWorker) for background writes, the window size (config.yaml: short_term_memory.short_term_mem_context_size, 10), and optionally a TurnLog. It reads no settings itself, which keeps it testable with fakes and easy to move out as a service later.

A step's outcome is never parsed from text. Each tool call's status comes from its ToolMessage: error when the tool raised ToolException, refused or declined from the approval gate, otherwise ok. A step with an error or refusal is failed, one the user declined is cancelled, anything else success.

Writing the turn log never blocks the reply and needs no LLM call. Only conversation turns skip steps, since an action's steps belong to the turn that ran them.

Episodes

An episode is one thing you wanted and everything around it, across as many turns as it took: the email that failed on auth, "try again", sent. It's stored as Observation → Action → Outcome. The LLM only groups turns and writes those three texts plus tags, people and importance. Everything the log already knows is filled in from the log: the status (the outcome of the last turn that acted, so a retried failure that worked is a success), the agents and tools, the times and the speaker. Turns the LLM leaves out stay unprocessed and come back next run, and an episode can name an earlier one it continues.

Why it changed (2026-11-11): the old Qdrant episodic and semantic stores embedded raw chat, wrong answers included, and pulled "facts" out of events with an extra LLM call per turn. Recall then surfaced old mistakes as truth. They and the fact extraction are gone: memory is now a structured log of what Karen actually did, with statuses taken from the tools.

Document retrieval (RAG)

  1. Ingestion (startup): DocumentLoader scans data/documents/<collection>/, optionally syncing from a GCS bucket first. It splits files and indexes only the ones not indexed yet into the Qdrant server (:6333), one collection per subfolder. A new server re-indexes everything once.
  2. Search: HybridRetriever.search(query) runs the vector search across all collections (top 20 candidates) and BM25 over the same documents.
  3. Fusion: weighted Reciprocal Rank Fusion merges the two rankings (BM25 0.4, semantic 0.6).
  4. Rerank: a cross-encoder (ms-marco-MiniLM-L-6-v2) keeps the best 5.
  5. Gate: documents go into the prompt only if the best cosine score reaches similarity_threshold (0.3). They're wrapped as untrusted documents data.

Each action is one line: when, which agent, the task, the outcome, the reason if it failed (the failing tool's result) and the tools it used, e.g. [2026-11-10 22:09] email: send an email to … — success [tools: send_email].

Scope to know about: short-term memory is one deque per process, not per thread_id. That's fine with you as the only user, but it's what would need changing if Karen ever served several people or parallel sessions. The turn log already records the speaker and thread of every turn.
