Karen: the LangGraph

One compiled graph handles every message. It's a hub-and-spoke loop: the router classifies the message, the supervisor plans and steps through the agents, and every turn ends in store_memory. Built in orchestrator/builders.py.

Even conversation turns pass through the supervisor, which passes them straight through when route == "conversation". The only loop is supervisor ⇄ action_handler.

The supervisor loop

The supervisor is a small state machine. The value of route tells it which phase it's in, so no extra flag needs to survive between turns.

route on entryMeaningSupervisor does
"conversation"The router picked chatPasses through to conversation_graph
"action"First entry this turnPlan: one LLM call returns [{agent, task}, …]. It saves original_query, resets the results, and dispatches step 1
an agent name, e.g. "reminder"Re-entry: that agent just ranStep: adds response to agent_results and marks the context untrusted if that agent's output is untrusted. Then it dispatches the next step, or finishes
"complete"Set by the supervisor itselfThe graph edge goes to store_memory

Dispatch sets route to the agent, narrows query to that step's sub-task, and clears response. Earlier results are wrapped as untrusted data, and the message list is cleared so each agent starts fresh. Finish restores original_query, joins the results into response, and sets route = "complete". Runaway plans are cut off by _MAX_STEPS = 8 and recursion_limit = 25.

stateDiagram-v2
  [*] --> Plan: route = action
  Plan --> Dispatch: plan[0]
  Dispatch --> AgentRuns: route = agent, query = task
  AgentRuns --> Step: re-enter supervisor
  Step --> Dispatch: plan not empty and steps under 8
  Step --> Finish: plan empty or step guard hit
  Finish --> [*]: route = complete

Agent subgraphs

ReAct agents: reminder, system, terminal, music, email

All five are built by AgentBase.build_react_graph() and share one shape. The model calls tools until it stops asking for them, and the last message becomes response. Every tool call passes the gate first, which decides from the tool's risk and who is speaking (core/tools.py: PERMISSIONS): run it, ask you first, or refuse.

Gate decisionWhen (today)What happens
runOwner calling a low or medium tool: almost everythingThe calls run
approveOwner calling a high tool: send_emailinterrupt() lists every such call in the message. Yes runs them all; anything else tells the model you declined
refuseA guest calling a medium or high tool, or family calling a high oneNothing in that message runs. The model is told it isn't allowed for this person

The gate and ask nodes route with Command(goto=...). VirtualAssistant.run() sees a pending interrupt and returns {pending: true, question}, and the next message from the user resumes it with Command(resume=answer).

Email only changes how a send reads in the question (To, Cc, Subject, Body, then "Send it? (yes/no)"), and it binds ask_user (can_ask = True). Other tools get a generic "You are about to run <tool>:" with their arguments. Both add the hidden-character warning, and the web-research warning when research ran earlier in the plan.

Everything before interrupt() in a node runs again on resume. Keep that part free of side effects. The code is written that way, and it's a rule to keep in mind for any new approval-gated agent.

Research: plan and execute on its own state

This one runs on ResearchAgentState, not GraphState. ResearchAgentWrapper converts between the two. The research supervisor makes a plan of questions, the search step calls Tavily for each one, and the loop ends after at most 3 iterations with a synthesized answer. Its output is marked untrusted_output because it's built from web content.

MCP status: a single node

build() returns a plain function, not a subgraph. It pings Veronica, reloads the tool list into MCPToolRegistry, and reports whether Veronica is online or offline.

Concept: one agent loop not built

This is a proposal, not the current design. It's decision #25 in Design decisions, drawn out so it can be judged before any code changes. Everything above this section describes what runs today.

Today a turn passes up to three layers of LLM calls before anything happens: the router picks conversation or action, the supervisor plans which agents to run, and each specialist agent runs its own tool loop. In the concept, one model sees every tool and decides in a single call whether to answer, call a tool, or ask you. Choosing the route becomes part of the same call that does the work. The OpenAI, Anthropic and Cognition guides recommend this as the default, adding agents only when one agent demonstrably fails.

The time saved is the router and supervisor calls. Whether the agent calls themselves get faster or slower depends on prompt length and caching (next diagram); that's the part to measure.

Prompt layout: why the order matters

    direction TB

  end

    s1["tool calls and their results"]

Each call shares the fixed part, so a server that reuses a cached prompt start only has to read the rest. That's the main speed gain the concept depends on. Caveat: Bonsai's hybrid architecture can't reuse a cached prompt start today (about 510 of 520 tokens reprocessed per call), and Qwen3.5 is hybrid in the same way. With all 19 tool definitions in every call, a single-tool request could get slower on Bonsai unless the --checkpoint-min-step experiment works or a model with plain attention throughout is used.

Risks

  • Tool choice on a local model. OpenAI's guide says some systems handle more than 15 distinct tools while others struggle with fewer than 10 overlapping ones. Karen has 19, and system and terminal overlap. Small models are where wrong tool choice shows up first.
  • Longer prompts per call. Every call carries all the tool definitions. Without caching this costs time on every step (see the caveat above).
  • One prompt holds every rule. Rules that live in five agent prompts today must coexist without contradicting each other.
  • Chat may lose document context. If retrieval becomes a tool, the model has to decide to search.

How to decide

  1. A test set of turns, extending the 16-query routing benchmark: chat, one tool, multi-step, approval, a refused guest call, a document question. For each turn, record whether it was correct, the seconds, the LLM calls and the prompt tokens.
  2. Build the loop alongside the current graph, behind a config switch (graph or loop), with no other changes.
  3. Run both on Bonsai, and on a model with plain attention throughout so caching works.
  4. Keep the loop only if it's at least as correct and faster. If tool choice is the weak point, try a cheap non-LLM step that picks the relevant tool groups first, before going back to an LLM dispatcher (Google's coordinator pattern).

Open questions

  • Send all 19 tools, or pick tool groups per turn? Decision #25 suggested picking groups once there are more than about 20.
  • Document retrieval: always run it for chat, or make it a tool?
  • Thinking: on for every step, or off for simple tool calls?
  • Memory extraction runs on the same model after each turn. Should it wait until Karen is idle?

Checkpointing and threads

  • The graph and every subgraph compile with the same InMemorySaver, keyed by thread_id. The CLI uses "session-001"; the API takes thread_id in the request.
  • Checkpoints make interrupts possible: a paused approval (an email send) is waiting in the saver.
  • Because it's in memory, a restart loses paused threads. KAREN_ENV=prod currently raises NotImplementedError; a Redis or Postgres saver would go there.
