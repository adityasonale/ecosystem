Karen: the LangGraph

One compiled graph handles every message: a single agent loop. One model sees every tool and decides, call by call, whether to answer, call a tool or ask you, and every turn ends in store_memory. Built in orchestrator/loop.py (LoopAgent.build_graph).

The loop replaced the router, the supervisor's fixed plan, the conversation graph and the five specialist agents (decision #25 in Design decisions). That design is kept at Karen's git tag supervisor-final; the comparison that decided it is under Measured.

The loop runs until the model replies without calling a tool. After 5 tool rounds in one request (_MAX_TOOL_ROUNDS), the next call has no tools bound and must answer, so a model that keeps retrying refused calls still replies inside recursion_limit = 25.

What the loop binds

Every tool in the ToolRegistry (see Tools and agents), plus two tools that wrap agents:

  • Local tools: reminders, time, date, battery, run_command, and search_documents. search_tool (Tavily) isn't bound directly; research uses it.
  • Veronica's MCP tools that have a tool_policy entry (email, music). An unlisted MCP tool isn't bound. veronica__ping isn't bound either, because check_connection covers it.
  • research: the research agent below, as one tool. Its answer comes back wrapped as untrusted.
  • check_connection: MCPStatusAgent.check_node. It pings Veronica, reloads her tools into the registry, and reports online or offline.
  • ask_user: bound to the model but never executed; ask answers it with an interrupt.

The gate

Every tool call passes the gate first. It decides from the tool's risk and who is speaking (core/tools.py: PERMISSIONS): run it, ask you first, or refuse. research and check_connection aren't in the registry, so the gate lets them run.

Gate decisionWhen (today)What happens
runOwner calling a low or medium tool: almost everythingThe calls run
approveOwner calling a high tool: send_emailinterrupt() lists every such call in the message. Yes runs them all; anything else tells the model you declined
refuseA guest calling a medium or high tool (including search_documents), or family calling a high oneNothing in that message runs. The model is told it isn't allowed for this person

The approval question reads "You are about to run <tool>:" with the arguments, sanitized, then "Go ahead? (yes/no)". It adds a hidden-character warning when an argument has one, and a web-research warning when untrusted_context is set. The gate and ask nodes route with Command(goto=...). VirtualAssistant.run() sees a pending interrupt and returns {pending: true, question}, and the next message from the user resumes it with Command(resume=answer).

Everything before interrupt() in a node runs again on resume. Keep that part free of side effects.

Research: plan and execute on its own state

Research stays a separate agent because it reads untrusted web pages in its own context and returns only a summary. It runs on ResearchAgentState, not GraphState, compiled without a checkpointer. The loop's research tool calls it through ResearchAgentWrapper. The research supervisor makes a plan of questions, the search step calls Tavily for each one, and the loop ends after at most 3 iterations with a synthesized answer. Thinking is on for this role only.

    s1["tool calls and their results"]
  end
  fixed --> perturn --> perstep

Each call shares the fixed part, so a server that reuses a cached prompt start only has to read the rest. On Qwen3.5 this works through llama-server's context checkpoints and RAM prompt cache, as long as the system message stays the same from call to call. The Memory: section is left out when memory is empty: an empty one made the model answer "What time is it?" without calling current_time. Caveat: Bonsai's hybrid architecture couldn't reuse a cached prompt start (about 510 of 520 tokens reprocessed per call), so with every tool definition in every call, a loop step costs more there.

Measured (2026-11-17, Qwen3.5-9B)

This comparison decided the switch. Karen's agent benchmark ran 27 end-to-end cases through VirtualAssistant.run() with the real model and prompts but fake tools: same names and schemas, canned results, nothing sent or saved. Cases were scored on behaviour (tools run, arguments, order, approvals, questions, the reply), never on which agent ran, so one set scored both designs. Each case ran 3 times. The results files are on Karen's main (evaluation/results/agents-*.json); the benchmark script itself was never committed.

  • The supervisor's one failure was structural: its plan was fixed before anything ran, so the email step ran after the reminder failed, in every run.
  • The loop's failures: "What time is it?" answered without calling current_time (0/3); "what time is it, and remind me in 2 hours" lost one of its two requests (0/3); and once, parallel tool calls sent the email before the failed reminder came back.
  • Prompt sensitivity: small wording changes move tool choice on a 9B model, so every prompt change needs a benchmark run.
  • Document retrieval was missing from the loop when this ran. It has since been added as the search_documents tool; the numbers above don't include it.

Next: rebuild the benchmark with document questions; turn off parallel tool calls so each step sees the last result; give the current time in the prompt next to the date.

Open questions

  • Picking tools per turn. Every call sends every tool. Once there are too many for the model to choose well, pick tool groups per turn (ToolSpec.group), for example by matching the message against tool descriptions in a vector store.
  • Document context in chat. The model has to decide to search; the conversation graph searched on every chat turn. Not measured yet.
  • Thinking: off for every loop step today. Worth trying on for multi-step requests?
  • Memory extraction runs on the same model after each turn. Should it wait until Karen is idle?

Checkpointing and threads

  • The graph compiles with an InMemorySaver, keyed by thread_id. The CLI uses "session-001"; the API takes thread_id in the request.
  • Checkpoints make interrupts possible: a paused approval (an email send) or question is waiting in the saver.
  • Because it's in memory, a restart loses paused threads. KAREN_ENV=prod currently raises NotImplementedError; a Redis or Postgres saver would go there.
