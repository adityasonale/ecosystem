The ecosystem

Four services, each with one job. Karen decides what to do, the gateway decides who may call which model, llm-server does the language-model work, and Veronica touches the outside world. They connect only over HTTP, so any one of them can be swapped out, moved to another machine, or reused by a new client.

Karen

The personal assistant: a LangGraph orchestrator that routes, plans, runs agents, and remembers.

client · :8000 in API mode

Gateway

LiteLLM Proxy: the front door for every model call, with a key, limits and a usage log per client.

gateway · :4000

llm-server

Serves local models behind an OpenAI-compatible API. It starts the right backend for each model and accepts only the gateway's key.

model host · :8100

Veronica

An MCP tool server that holds the OAuth tokens and calls Gmail and Spotify.

tool server · :8200

Infrastructure

llama-server (Qwen3.5 9B), Redis + Celery, Qdrant (server), SQLite.

:6333 · :6380

Who owns what

ConcernOwnerWhy there
Deciding what to do with a messageKarenOrchestration is the assistant's job. Routing, planning and memory all stay in one place.
Who may call a model, how often, and usage per clientgatewayOne virtual key per client, with rate limits and budgets, kept apart from the code that runs models. Hosted models can be added here later without breaking llm-server's local-only rule.
Which model runs, and howllm-serverKaren only names a model (qwen3.5-9b). llm-server maps the name to a path in models.yaml, picks a backend plugin, and starts it. Swapping models is a models.yaml change.
Model weights, the GPU, inferencellama-serverllama.cpp already does streaming and tool calling well. llm-server forwards to it rather than reimplementing it.
Third-party credentials (Google, Spotify)VeronicaOAuth tokens live in one service. Any MCP client (Karen, Claude, a future app) reuses the same tools.
What Karen can doKaren CapabilityCatalogBuilt live from the registered agents and whichever MCP tools are connected, never from a hand-kept list.
Long-running and timed workCelery + RedisA reminder must fire even if the process that created it is busy. Startup reschedules any pending reminders from SQLite. Episodes are built on a separate worker so an LLM call never delays a reminder.

Locally, python -m main starts the rest first from config.local.yaml: ecosystem: Redis, Qdrant (container qdrant-ecosystem, port 6333), the Celery worker, the memory worker, Celery beat, llm-server, the gateway and Veronica. Ones already running are reused.

All projects run from the shared ~/projects/dev-venv until they're deployed separately.
