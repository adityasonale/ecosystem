Request flows

Three messages followed end to end, then what happens when a part is down. Each LLM call is one round trip through the gateway to llm-server, and at about 10 tok/s on the local model, the number of LLM calls per turn is the main cost.

1. Conversation: "what did we talk about yesterday?"

sequenceDiagram
  autonumber
  actor U as You
  participant CLI as CLIInterface
  participant VA as VirtualAssistant
  participant G as Graph (agent loop)
  participant DB as SQLite
  participant L as gateway / llm-server
  U->>CLI: message
  CLI->>VA: run(query, thread_id)
  VA->>G: invoke({query, speaker})
  G->>DB: recall: 3 latest + similar older episodes, steps not built yet, recent exchanges
  G->>L: agent: persona, rules, every tool, memory, query
  L-->>G: reply, no tool calls
  G->>G: finish (route = conversation) → store_memory (short-term now, turn log queued)
  G-->>VA: {response, route}
  VA-->>CLI: {pending: false, response}
  CLI-->>U: speak or print

1 LLM call. A question about your documents adds a search_documents call (Qdrant and BM25) and a second LLM call to answer from the passages; the model decides when to search. Writing the turn log happens after the reply is returned and needs no LLM call.

2. Action: "remind me to call mom at 6pm"

sequenceDiagram
  autonumber
  participant G as Graph (agent loop)
  participant L as gateway / llm-server
  participant DB as SQLite
  participant R as Redis
  participant C as Celery worker
  participant A as API /events
  G->>L: agent with every tool
  L-->>G: tool_call create_reminder(6pm)
  Note over G: gate: medium risk, owner → run
  G->>DB: insert Reminder (due_at in UTC)
  G->>R: fire_reminder.apply_async(eta)
  G->>L: agent sees the tool result
  L-->>G: "Done, I'll remind you at 6pm"
  Note over G: finish (route = complete, one step) → store_memory
  Note over C: later, at 6pm
  R->>C: fire_reminder(id)
  C->>DB: load reminder
  C-->>C: Discord webhook, speak (each if in reminders.channels)
  C->>R: publish a reminder event on karen:events
  R->>A: forward to every connected client (SSE)
  C->>DB: mark done

2 LLM calls: one picks the tool, one writes the reply. The reminder itself doesn't depend on Karen being alive at 6pm, and pending reminders are rescheduled from SQLite when Karen starts. How it's delivered comes from config.yaml: reminders.channels, not from which --mode Karen runs in; each channel fails on its own without stopping the others.

3. Multi-step with approval: "research X and email me a summary"

sequenceDiagram
  autonumber
  actor U as You
  participant VA as VirtualAssistant
  participant G as agent loop
  participant RS as research agent
  participant V as Veronica
  U->>VA: request
  VA->>G: invoke
  G->>G: LLM calls the research tool
  G->>RS: research(question)
  RS->>RS: plan questions → Tavily searches → synthesize
  RS-->>G: answer, wrapped as untrusted (untrusted_context = true)
  G->>G: LLM drafts a veronica__send_email call
  Note over G: gate: high risk, owner → approve
  G-->>VA: interrupt: "You are about to run ... (web-research warning) Go ahead?"
  VA-->>U: {pending: true, question}
  U->>VA: "yes"
  VA->>G: Command(resume="yes")
  G->>V: veronica__send_email
  V-->>G: {id, threadId}
  G->>G: LLM writes the reply → finish → store_memory
  G-->>U: final response

The security boundary: web content reaches the loop that can act outside Karen. Wrapping it as untrusted data helps but isn't reliable, so the real control is that you approve every send. That approval comes from send_email being high risk: every tool call passes the same gate, so any high-risk tool asks first. Because the loop sees each result before the next step, a failed step can stop the steps that depend on it; the old supervisor's fixed plan couldn't.

4. What happens when something is down

Local model busy503 + Retry-AfterThe gateway retries twice, then Karen's client retries with backoff
Gateway downKaren's model calls fail (connection refused) and the turn ends with an error message. llm-server can't be called directly, because it accepts only the gateway's keyChatOpenAI retries twice; restart with docker compose up -d --wait
A tool, mid-call (Veronica stops answering, a bug)Only that call fails; other calls of the same reply keep their results. The model is told the call may or may not have completed and not to retry it_tool_failed in orchestrator/loop.py (ToolNode's handle_tool_errors); the exception is logged. A tool's own ToolException, including Veronica's MCP errors, still reaches the model as its message
