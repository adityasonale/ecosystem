Request flows

Four messages followed end to end. Each LLM call is one round trip through the gateway to llm-server, and at about 10 tok/s on the local model, the number of LLM calls per turn is the main cost.

1. Conversation: "what did we talk about yesterday?"

sequenceDiagram
  autonumber
  actor U as You
  participant CLI as CLIInterface
  participant VA as VirtualAssistant
  participant G as Graph
  participant Q as Qdrant
  participant DB as SQLite
  participant L as gateway / llm-server
  U->>CLI: message
  CLI->>VA: run(query, thread_id)
  VA->>G: invoke({query})
  G->>L: router: classify_route
  L-->>G: "conversation"
  Note over G: supervisor passes through
  G->>Q: hybrid search (vector + BM25, rerank)
  G->>DB: recent actions (last 5 steps, turn log)
  G->>L: converse(query, memory, docs?, known systems)
  L-->>G: reply
  G->>G: store_memory (short-term now, turn log queued)
  G-->>VA: {response, route}
  VA-->>CLI: {pending: false, response}
  CLI-->>U: speak or print

2 LLM calls, both on the critical path. Writing the turn log happens after the reply is returned and needs no LLM call.

2. Action: "remind me to call mom at 6pm"

sequenceDiagram
  autonumber
  participant G as Graph
  participant L as gateway / llm-server
  participant RA as reminder_graph
  participant DB as SQLite
  participant R as Redis
  participant C as Celery worker
  participant A as API /events
  G->>L: router
  L-->>G: "action"
  G->>L: supervisor: plan_actions
  L-->>G: [{agent: reminder, task: ...}]
  G->>RA: dispatch (route = reminder)
  RA->>L: agent with tools
  L-->>RA: tool_call create_reminder(6pm)
  RA->>DB: insert Reminder (due_at in UTC)
  RA->>R: fire_reminder.apply_async(eta)
  RA->>L: agent sees the tool result
  L-->>RA: "Done, I'll remind you at 6pm"
  RA-->>G: response
  Note over G: supervisor step → plan empty → complete → store_memory
  Note over C: later, at 6pm
  R->>C: fire_reminder(id)
  C->>DB: load reminder
  C-->>C: Discord webhook, speak (each if in reminders.channels)
  C->>R: publish a reminder event on karen:events
  R->>A: forward to every connected client (SSE)
  C->>DB: mark done

4 LLM calls: router, supervisor, and 2 ReAct steps. The reminder itself doesn't depend on Karen being alive at 6pm, and pending reminders are rescheduled from SQLite when Karen starts. How it's delivered comes from config.yaml: reminders.channels, not from which --mode Karen runs in; each channel fails on its own without stopping the others.

3. Multi-step with approval: "research X and email me a summary"

sequenceDiagram
  autonumber
  actor U as You
  participant VA as VirtualAssistant
  participant S as supervisor
  participant RS as research_graph
  participant EM as email_graph
  participant V as Veronica
  U->>VA: request
  VA->>S: router → action → plan
  Note over S: plan = [research, email]
  S->>RS: task 1
  RS->>RS: plan questions → Tavily searches → synthesize
  RS-->>S: answer (untrusted_output)
  S->>EM: task 2, with research output wrapped as untrusted data
  EM->>EM: LLM drafts send_email tool call
  EM-->>VA: interrupt: "Send to ..., subject ...? (yes/no)"
  VA-->>U: {pending: true, question}
  U->>VA: "yes"
  VA->>EM: Command(resume="yes")
  EM->>V: veronica__send_email
  V-->>EM: {id, threadId}
  EM-->>S: "Sent"
  S->>S: join results → complete → store_memory
  S-->>U: final response

The security boundary: web content goes into an agent that can act outside Karen. Wrapping it as untrusted data helps but isn't reliable, so the real control is that you approve every send. That approval comes from send_email being high risk, not from code in the email agent: every ReAct agent passes each tool call through the same gate, so any high-risk tool asks first wherever it's bound.
