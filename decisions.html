Design decisions

The record of choices: what was decided, what was considered instead, and why. When you're about to change one of these, read the reasoning first; if it no longer holds, write the new decision here.

#DecisionRejectedWhy
1All LLM calls go through llm-server, using the OpenAI chat APILangChain provider classes in each project; LiteLLMOne place for models, keys, limits and tracing, and every client uses the standard format. LiteLLM is the production standard, but llm-server is a learning and portfolio project, so building it is the point. Amended by #32: LiteLLM now sits in front, for clients and limits; llm-server still runs the models.
2Local models onlyGroq and other hosted APIsSmall local models are now good enough to be worth investing in. No per-token cost, and data stays on the machine. Hosted APIs can come back later as one more upstream entry.
3llm-server forwards to llama-server rather than running GGUF itselfA GGUF loader inside llm-serverllama.cpp already does streaming, tool calling and fast kernels (PQ2_0). The gateway's job is routing, not inference. Since #27, llm-server starts and stops llama-server too, but inference still happens in the separate process.
4Model chosen by a provider/model prefix, replaced by #27. The prefix still works as an alias.A separate provider fieldIt stays within the OpenAI request shape, so off-the-shelf SDKs work unchanged.
5Keep LangChain only as a thin client (ChatOpenAI) in KarenRemoving LangChain completelyLangGraph's ReAct and ToolNode expect LangChain messages and tools; ChatOpenAI(base_url=…) is just an HTTP client.
6Agent registry: one list generates routes, nodes and promptsEditing 6 places to add an agentWhen the same fact lives in several places, those places drift apart. Duplicate routes now fail at startup.
7Capabilities are built live from agents and MCP toolsHand-kept INTERNAL_CAPABILITIES / EXTERNAL_SYSTEMSThe prompt never claims a tool that isn't connected.
8SystemAgent with real tools for time, date and batterygeneral_action, a catch-all routeA catch-all route hides misroutes; specific tools can be tested.
9Speaking belongs to the interface, not the graphspeak nodes inside the conversation graphThe graph returns text; CLI, Discord and API each decide how to deliver it.
10Per-machine config: config.local.yaml deep-merged over config.yamlEditing paths in the shared fileThe Mac and Windows machines have different paths; the shared defaults stay portable (HF model IDs).
11Human approval for every outbound emailDefending with prompts aloneWeb content can reach the email agent; a prompt can't be relied on to stop an injection.
12Third-party credentials live only in VeronicaOAuth inside KarenOne place to protect and refresh tokens; any MCP client can reuse them.
13No Go layer between the servicesA Go service connecting Karen, Veronica and llm-serverThe time goes into inference at about 10 tok/s, not into Python overhead. A new layer adds a hop and something else to run without making anything faster.
14Log fingerprints, never secretsLogging rejected keysA key was found in a committed log file. Logs now hold sha256:xxxxxxxx len=N, logs/ is gitignored, and the keys were rotated.
15One shared dev-venv during developmentA venv per projectAvoids installing torch several times. Each project keeps its own requirements file for when it's deployed separately.
16The coding agent was dropped (see #28 for the read-only terminal that came after)Keeping a sandboxed coding agent in KarenNot part of what Karen is for, and it was the largest attack surface.
17Memory is one package behind one object (Memory)Agents reading the deque and the Qdrant record layout directlyMemory was spread over six places. Now agents call four methods, record layouts live in one file and prompt text in another. This also makes a later move to a separate service mechanical.
18Memory stays inside Karen for nowA memory service right away; writing it in GoOnly Karen uses it. Becomes a service when a second assistant arrives. Go wouldn't help: recall takes about 20–50 ms of embedding and Rust-based Qdrant work, against seconds of LLM time.
19Document search stays separate from memoryMerging RAG into the memory layerThey differ in who writes them, how they're searched, and how far they're trusted. Documents are wrapped as untrusted; memory isn't. They meet only in the conversation prompt.
20Who you are goes in a small profile that's always in the prompt, not found by searching your resumeEmbedding search over resume chunks; an about_user router flagChatGPT, Claude and Letta all keep a short profile always in context and fetch large history only on demand. "Tell me about myself" barely resembles resume chunks. Cap it at about 200 tokens. Cost on Bonsai depends on prompt caching.
21Interfaces identify the speaker; the core receives a speaker_idYour name hardcoded in each personaLeaves room for voice recognition and several people later. An unknown speaker is a guest, never the owner. Names stay in the gitignored config.local.yaml.
22Agents report only through response; only the supervisor writes agent_resultsResearch writing its results directlyThe direct write duplicated results and hid the web-research warning on email approvals.
23Veronica's REST /send-email only emails the owner (recipient allowlist)A human approval step on the REST route; removing itIts only job is notifications to you, and an approval step would defeat that. An allowlist keeps automation working and means a leaked key can't email anyone else. Email to anyone else goes through MCP, where Karen asks you.
24Tools are the unit: one ToolRegistry describes every tool with a group, a risk and labels (untrusted output, asks the user); agents bind by groupEach agent filtering tool names its own way (a substring, an allowlist, direct imports)Three filters drifted: the email gate asked for approval on reads. The labels let one place enforce approval, which the single loop needs. MCP labels live in Karen's tool_policy until Veronica sends MCP annotations.
25Target: one agent loop over all tools, with a separate agent only when it earns it (its own multi-step workflow, or isolating untrusted content: research). Agreed, not built. Drawn out under Concept: one agent loop.A new agent node for every ability; keeping the router and the supervisor's fixed planFixed nodes mean Karen can only do what a node was written for, can't change course after a result, and every ability needs graph changes. A loop combines tools on its own. Risk: on Bonsai every step re-reads every tool's description (about 25–45 tok/s), so the loop is built alongside the current graph and kept only if a test set says it wins.
26Risk levels (low, medium, high) instead of a yes/no approval flag, plus a permission table (who is speaking × risk → run, ask first, refuse) enforced by one gate in every ReAct agentA requires_approval flag checked only in the email agent; relying on the prompt's guest ruleOne judgement per tool drives approvals now and per-speaker permissions later, and maps onto MCP annotations. The gate in the shared base closes the gap where a high-risk tool outside email would run unasked. Unknown tools are high. Family is refused high-risk calls rather than approving the owner's outward actions.
27Model loading is a plugin chosen per model by format and hardware. Clients name a model; models.yaml maps names to paths. llm-server starts the backend on demand and keeps one model resident.The client picking the backend with a prefix; one hardcoded loader; models listed in settings.py; preloading at startupThe same GGUF runs on the Mac and the 8 GB laptop, and HF or MLX folders need other runtimes. A plugin per runtime keeps that choice in llm-server. Backends run as their own OpenAI-compatible servers, so tools and streaming pass through unchanged. models.yaml is per machine because the paths differ. It's re-read on change, so no restart is needed.
28A read-only terminal agent: allowlisted commands with checked arguments, no shell, paths limited to ~/projects, secrets denied, enforced in tools/terminal_tools.py. Read-only is medium risk (runs for the owner and family, refused for guests). Anything that changes state comes later as separate high-risk tools you approveA full shell with approval on every command; a sandboxed shell (the old sbx setup); typed tools only; read and write access in v1Most of what you'd ask a voice assistant about a computer is a question about state (disk, processes, git, finding a file), and an allowlist handles reads well. This keeps the reason for #16 in view: a shell is the largest attack surface, and research output can reach later steps. So the restriction lives in code, and the output is untrusted. A shell or python on the allowlist would make it pointless, so neither is there; nor are network tools, so nothing can send data out.
29Clients (a HUD, an app) get live events from Karen's API as Server-Sent Events (GET /events), fed by a Redis pub/sub channel any process can publish to; GET /reminders?fired_since= catches them upKaren calling a webhook the client exposes; WebSockets; each client pollingThe API is meant to be the one backend every client reuses. Browser, desktop and phone clients can't receive incoming calls, but they can all hold a connection open. SSE is one-way, which is all notifications need (chat stays on POST /chat), and it reconnects on its own. The worker and the API are separate processes, so Redis, already running, carries events between them. WebSockets can come later if chat or voice streaming needs a two-way connection.
30Reminder delivery is set in config (reminders.channels: discord, speak, events), not by --modeThe worker reading the mode Karen last wrote to RedisOne Redis value for a running mode was wrong in three ways: api mode delivered nothing, two interfaces running at once overwrote each other, and the value stayed after Karen exited. --mode now only picks the interface.
31llm-server eval runs are recorded only as local .jsonl files; MLflow and its model registry were removed. LangSmith stays for tracingKeeping MLflow for eval tracking; moving evals to LangSmith nowMLflow only copied four numbers the results file already holds, wasn't even in requirements.txt, and its registry was dead: nothing read the champion alias and the benchmark run it needed was deleted. LangSmith (or self-hosted Langfuse) evals are an option later, if comparing runs needs a UI.
32A separate gateway (pinned LiteLLM Proxy + Postgres, ~/projects/gateway, :4000) in front of llm-server. It owns clients, virtual keys, rate limits, budgets and usage per client; one wildcard route forwards every model name to llm-server, whose API_KEYS now holds only the gateway's key. Veronica stays direct.Building users and limits into llm-server; LiteLLM inside llm-server's repo; LiteLLM as a Python library inside llm-server; putting Veronica's MCP tools behind it nowSeveral clients with their own keys and limits is a solved problem, and LiteLLM's proxy already does it. The library alone only routes. A separate project keeps llm-server local-only (#2) while hosted models can be added at the gateway later. One wildcard route means models.yaml stays the only list of local models. The image is pinned because it sits on every model call. Veronica already has per-client keys and one client, and moving it would change Karen's MCP transport and tool names.

Open questions

  • Persistent checkpointer: paused approvals are lost on restart. Redis is already running.
  • Latency: 4+ LLM calls per action turn at about 10 tok/s. Merging the router and supervisor was tried and was slower, because Bonsai's hybrid attention didn't reuse the prompt cache. Parked for now.
  • Where Karen runs: the Mac (Metal), the 8 GB GPU laptop, or the GCP VM. This decides where llm-server and llama-server run too.
  • How tools reach the loop: send all of them while there are few (19 today) (short descriptions, fixed prompt start so caching can work), or pick groups per turn by embedding once there are more than about 20. Decided after measuring token counts and step times on Bonsai and Qwen 3.5 9B.
  • Profile growth: extract it from your resume, update facts Mem0-style (add, update or replace), and keep it capped. Today the profile is only your name and relationship.
